## 1. 목표와 표기

첫 버전은 **AI 사용량 반영 → 재화 획득 → 선수 카드 구매 → 선수단 구성 → 이름·사진 변경**의 흐름을 완성하는 것을 목표로 제안한다. 앱을 다시 실행해도 진행 내용이 유지되어야 한다.

원문의 확정 사항과 제안을 구분한다. 아래 체크박스는 **구현 완료 여부**이며, 제안이 승인되었다는 뜻이 아니다. 아직 완료된 구현은 없다.

| 표기 | 의미 |
| --- | --- |
| 확정 | 기획서 §2의 확정 요구사항 |
| 기획 제안 | 기획서에서 제안한 구조·화면·상세 동작·첫 버전 범위 |
| 구현 제안 | 해당 기능을 안정적으로 구현하기 위해 이 목록에서 추가한 작업 |
| 결정 필요 | 정책을 정해야 동작과 완료 기준을 확정할 수 있는 항목 |

개발 언어, UI 프레임워크, 저장 기술은 아직 정하지 않는다. 아래 완료 기준은 제안 항목을 채택했을 때의 기준이다.

## 2. 기능 체크리스트

### A. macOS 앱 기본 구조와 저장

- [ ] `APP-01` **[확정] macOS 앱 실행** — Mac에서 TokenBaseball을 실행할 수 있다.
- [ ] `APP-02` **[기획 제안] 주요 화면 이동** — 홈, 카드 상점, 보유 카드, 카드 상세, 내 선수단, 설정에 접근할 수 있다. 카드 상세는 보유 카드에서 진입한다.
- [ ] `APP-03` **[기획 제안] 진행 내용 저장·복원** — 재화, 보유 카드, 선수단, 수정한 이름과 사진이 앱 종료·재실행 후에도 유지된다.
- [ ] `APP-04` **[구현 제안] 토큰·지급 기록 저장** — 인정한 사용량과 재화 지급 기록을 함께 보존해, 재실행 후 같은 기록이 다시 들어와도 중복 지급을 막을 수 있다.
- [ ] `APP-05` **[구현 제안] 저장·불러오기 실패 처리** — 실패를 사용자에게 안내하고, 저장되지 않은 작업을 완료로 표시하지 않는다. 기존 저장 내용을 임의로 초기화하지 않는다.

**결정 필요:** 지원할 최소 macOS 버전, 개발 기술, 저장 방식. 배포 형태는 첫 배포 전에 결정한다.

### B. AI 토큰 사용량 반영

- [ ] `TOK-01` **[기획 제안] 사용량 반영 방식 1개 구현** — 선택한 AI 서비스의 사용량을 선택한 방식으로 앱에 반영할 수 있다. 자동 수집·파일 가져오기·수동 입력 중 어느 방식인지는 아직 정하지 않는다.
- [ ] `TOK-02` **[기획 제안] 인정 토큰량 계산** — 반영된 사용량에서 정책상 인정되는 토큰만 집계하고, 누적 인정 토큰량을 표시한다.
- [ ] `TOK-03` **[기획 제안] 중복 반영 방지** — 동일한 사용 기록을 다시 반영해도 누적 인정 토큰량과 지급 재화가 중복으로 늘지 않는다. 기록 식별 방법은 반영 방식에 맞춰 정한다.
- [ ] `TOK-04` **[기획 제안] 반영 상태·실패 안내** — 사용량 반영 상태를 표시한다. 가져오기에 실패하면 기존 사용량과 재화 잔액을 유지하고 원인을 안내한다.
- [ ] `TOK-05` **[구현 제안] 유효하지 않은 사용량 처리** — 음수, 숫자가 아닌 값, 해석할 수 없는 기록 등 선택한 방식에서 발생 가능한 오류를 검증하고 잘못된 재화를 지급하지 않는다.

**결정 필요:** 지원 AI 서비스, 수집·입력 방식, 입력·출력·캐시 토큰 인정 범위, 연동 이전 사용량 인정 여부. 자동 수집을 선택하면 갱신 시점과 주기도 정한다.

### C. 재화 계산과 잔액 관리

- [ ] `CUR-01` **[확정] 토큰 기반 재화 지급** — 인정한 AI 토큰 사용량에 따라 앱 내 재화를 획득한다. 환산 비율과 소수점 처리는 결정된 정책을 따른다.
- [ ] `CUR-02` **[기획 제안] 재화 항목 구분** — 누적 획득 재화, 사용한 재화, 보유 재화를 구분해 관리한다. 기획서 범위에서는 `보유 재화 = 누적 획득 재화 − 사용한 재화`를 만족한다.
- [ ] `CUR-03` **[기획 제안] 누적 사용량과 잔액 분리** — 카드를 구매하면 보유 재화만 줄어들고, 누적 인정 토큰량과 누적 획득 재화는 유지된다.
- [ ] `CUR-04` **[구현 제안] 사용량 인정과 지급의 일관성** — 지급 도중 저장에 실패하거나 앱이 종료돼도, 재시도 시 해당 사용량에 대한 재화가 빠지거나 두 번 지급되지 않는다.

**결정 필요:** 재화 명칭, 토큰당 환산 비율, 소수점·잔여 토큰 처리 기준. 환산 방식에 따라 같은 총사용량을 여러 번 나누어 반영할 때의 처리도 정의한다.

### D. 선수 카드 기본 정보

- [ ] `CRD-01` **[확정] 카드 등급 3개 지원** — 모든 선수 카드는 세 등급 중 하나에 속한다. 등급명은 미정이며, ‘루키 → 올스타 → 레전드’는 기획서의 제안이다.
- [ ] `CRD-02` **[확정] 초기 이름·사진 제공** — 선수 카드에 최초 가명과 기본 프로필 이미지를 제공한다.
- [ ] `CRD-03` **[기획 제안] 카드 식별값 관리** — 선수 이름이나 사진을 바꿔도 같은 보유 카드로 식별한다. 같은 선수의 카드를 여러 장 보유할 수 있도록 결정하면 각 보유 카드를 구별한다.
- [ ] `CRD-04` **[기획 제안] 포지션 정보 제공** — 선수단 배치에 참고할 수 있도록 카드에 수비 포지션을 표시한다. 포지션에 따른 배치 제한은 별도 정책으로 둔다.

**결정 필요:** 등급명 확정, 초기 카드 종류·수량, 등급별 희소성·가격 차이. 능력치는 첫 버전 필수 항목으로 두지 않는다.

### E. 카드 상점과 구매

- [ ] `SHP-01` **[기획 제안] 판매 카드 목록** — 구매 가능한 카드의 선수 정보, 등급, 가격을 확인할 수 있다.
- [ ] `SHP-02` **[확정] 재화로 선수 카드 구매** — 획득한 재화를 사용해 선수 카드를 구매하고 보유 카드에 추가할 수 있다.
- [ ] `SHP-03` **[기획 제안] 원하는 카드 직접 구매** — 구매할 카드 한 장을 선택하고 구매 전에 정보와 가격을 확인한다. 이 항목은 직접 구매 방식을 채택할 때 구현한다.
- [ ] `SHP-04` **[기획 제안] 잔액 부족 처리** — 재화가 부족하면 구매를 완료하지 않고, 필요한 추가 재화를 표시한다.
- [ ] `SHP-05` **[기획 제안] 구매 결과의 일관성** — 구매가 성공하면 재화 차감과 카드 지급이 함께 반영된다. 실패하면 둘 중 하나만 반영되는 상태가 생기지 않는다.
- [ ] `SHP-06` **[구현 제안] 구매 중 반복 요청 처리** — 처리 중인 구매 버튼의 연속 클릭으로 같은 구매 요청이 여러 번 실행되지 않는다. 완료 후 다시 구매할 수 있는지는 중복 구매 정책을 따른다.

**결정 필요:** 직접 구매·무작위 팩 지원 여부, 카드별·등급별 가격, 상점 노출 카드와 갱신 방식, 동일 선수 카드의 중복 구매 허용 여부. 팩을 채택하면 구성·확률·결과 표시 기능을 별도로 명세한다.

### F. 보유 카드 조회

- [ ] `INV-01` **[기획 제안] 전체 보유 카드 목록** — 구매한 카드가 목록에 나타나며, 선수단에 배치하지 않은 카드도 확인할 수 있다.
- [ ] `INV-02` **[기획 제안] 등급별 필터** — 전체 또는 특정 등급의 카드만 볼 수 있다.
- [ ] `INV-03` **[기획 제안] 카드 상세 보기** — 선택한 카드의 이름, 사진, 등급을 확인하고 이름·사진 변경과 선수단 등록으로 이어갈 수 있다. 포지션을 채택하면 함께 표시한다.
- [ ] `INV-04` **[구현 제안] 빈 목록 안내** — 보유 카드가 없거나 필터 결과가 없을 때 현재 상태를 설명한다. 보유 카드가 없으면 상점으로 이동할 수 있다.

### G. 선수 이름과 프로필 사진 변경

- [ ] `CUS-01` **[확정] 선수 이름 변경** — 보유 선수 카드의 이름을 사용자가 변경할 수 있다.
- [ ] `CUS-02` **[기획 제안] 이름 검증** — 공백만 있는 이름은 저장할 수 없으며 수정할 내용을 안내한다. 길이 제한은 정책 결정 후 적용한다.
- [ ] `CUS-03` **[확정] 프로필 사진 변경** — 보유 선수 카드의 프로필 사진을 사용자가 변경할 수 있다.
- [ ] `CUS-04` **[기획 제안] Mac 이미지 선택·미리보기** — Mac의 이미지 파일을 선택하고 적용 전에 표시 영역을 확인할 수 있다. 자르기 도구 제공 여부는 별도 결정한다.
- [ ] `CUS-05` **[기획 제안] 변경 내용 일괄 반영** — 이름과 사진 변경이 해당 카드의 목록·상세·선수단 표시에 함께 반영된다. 카드 등급과 식별값은 유지된다.
- [ ] `CUS-06` **[기획 제안] 기본값 복원** — 변경한 이름과 사진을 최초 기본값으로 되돌릴 수 있다.
- [ ] `CUS-07` **[구현 제안] 이미지 오류·취소 처리와 보관** — 선택 취소나 지원하지 않는 파일의 적용 실패 시 기존 사진을 유지한다. 적용한 사진은 원본 파일이 이동·삭제되어도 앱에서 다시 표시할 수 있도록 보관한다.

**결정 필요:** 이름 길이 제한, 이미지 형식·용량, 이미지 자르기 기능 여부, 동일 선수 카드를 여러 장 보유했을 때 변경 적용 범위.

### H. 내 선수단 구성

- [ ] `ROS-01` **[확정] 보유 카드로 선수단 구성** — 보유한 선수 카드를 선택해 선수단에 등록할 수 있다.
- [ ] `ROS-02` **[기획 제안] 기본 수비 9자리 표시** — 투수, 포수, 1루수, 2루수, 3루수, 유격수, 좌익수, 중견수, 우익수 자리를 제공한다. 9자리 구성을 채택할 때 구현한다.
- [ ] `ROS-03` **[기획 제안] 선수 교체·제외** — 등록한 선수를 다른 보유 카드로 교체하거나 선수단에서 제외할 수 있다. 교체·제외된 카드는 보유 목록에 남고 소비되지 않는다.
- [ ] `ROS-04` **[기획 제안] 같은 카드의 중복 배치 방지** — 동일한 보유 카드 한 장을 여러 자리에 동시에 배치할 수 없다. 동일 선수의 서로 다른 카드 허용 여부는 별도 정책으로 정한다.
- [ ] `ROS-05` **[기획 제안] 빈자리 유지** — 카드가 부족하거나 선수를 제외하면 자리를 비워 둘 수 있으며, 미완성 선수단도 저장된다.

**결정 필요:** 최종 정원, 포지션별 배치 제한, 지명타자, 선발·불펜 구분, 타순, 구단 이름 변경. 이 항목들을 확정 없이 첫 버전 필수 기능으로 추가하지 않는다.

### I. 홈과 설정

- [ ] `HOM-01` **[기획 제안] 홈 요약 정보** — 누적 인정 토큰량, 보유 재화, 선수단 구성 현황, 사용량 반영 상태를 확인할 수 있다.
- [ ] `HOM-02` **[구현 제안] 변경 후 화면 갱신** — 사용량 반영·구매·선수단 수정 후 관련 요약 값이 최신 상태로 표시된다.
- [ ] `SET-01` **[기획 제안] 사용량 반영 설정** — 선택한 반영 방식에 필요한 연결 또는 입력 설정을 제공한다. 계정 연결이 필요 없는 방식이면 로그인 기능을 임의로 추가하지 않는다.

## 3. 먼저 결정할 정책

미정 사항 때문에 모든 개발을 멈출 필요는 없다. 다만 아래 결정을 내리기 전에는 해당 기능의 실제 동작을 확정하지 않는다.

| 순서 | 결정할 사항 | 확정 전 가능한 작업 | 결정이 필요한 구현 |
| --- | --- | --- | --- |
| 1 | 지원 AI 서비스·반영 방식·인정 토큰 범위·과거 사용량 | 앱 구조와 데이터 흐름 설계 | 실제 사용량 반영, 기록 식별과 중복 방지, 연결·입력 설정 |
| 2 | 재화 명칭·환산 비율·소수점·잔여량 처리 | 재화 항목과 저장 구조 설계 | 지급 계산, 지급 내역 검증 |
| 3 | 구매 방식·카드 가격·중복 허용·상점 갱신 | 카드 정보 구조와 보유 목록 설계 | 상점 판매 방식, 구매 가능 조건, 팩 관련 추가 명세 |
| 4 | 등급명·초기 카드 구성·선수단 정원·배치 규칙 | 이름·사진 편집 구조 설계 | 초기 카드 데이터, 선수단 배치 검증 |
| 5 | 이름 길이·사진 형식·용량·변경 적용 범위 | 편집 흐름 설계 | 입력 검증, 이미지 보관과 적용 |
| 6 | 최소 macOS 버전·개발 기술·저장 방식 | 요구사항과 완료 기준 검토 | 앱 프로젝트 생성과 실행, 데이터 저장 구현 |

## 4. 권장 개발 순서

각 단계의 제안 채택과 관련 정책 결정을 전제로 한 순서다.

1. **기반 만들기:** 개발 기술을 정하고 macOS 앱 실행, 화면 이동, 카드·재화·선수단·사용 기록 저장 구조를 만든다.
2. **토큰과 재화 연결:** 사용량 반영 방식 1개를 구현하고 인정 토큰 계산, 중복 방지, 재화 지급을 연결한다.
3. **카드 구매 완성:** 3개 등급과 초기 카드 데이터를 구성하고 상점, 구매, 보유 카드 목록을 연결한다.
4. **선수단과 꾸미기 완성:** 카드 등록·교체·제외, 이름 수정, 사진 변경·복원을 연결한다.
5. **홈·설정과 오류 처리 마무리:** 요약 정보와 설정을 연결하고 빈 화면, 실패, 재실행 시 동작을 확인한다.

개발용 사용량과 카드 데이터는 실제 사용 기록과 구분한다. 실제 사용량 반영 방식이 동작해야 첫 버전의 전체 흐름이 완료된 것으로 본다.

## 5. 첫 버전 완료 검증

아래는 위 제안을 채택한 첫 버전의 검증 목록이다. 기능을 별도로 추가하는 목록이 아니다.

- [ ] 선택한 실제 반영 방식으로 사용량을 가져와, 결정한 환산 정책에 맞는 재화를 획득한다.
- [ ] 같은 사용 기록을 다시 반영하거나 앱 재실행 후 반영해도 토큰과 재화를 중복 계산하지 않는다.
- [ ] 재화가 충분하면 카드를 구매하고, 부족하면 구매를 막으면서 부족액을 표시한다.
- [ ] 구매·재화 지급 중 실패나 반복 요청이 있어도 카드와 잔액이 어긋나지 않는다.
- [ ] 구매한 카드를 선수단에 등록·교체·제외할 수 있고, 같은 카드 한 장의 중복 배치를 막는다.
- [ ] 이름·사진 수정과 기본값 복원이 관련 화면에 반영되고 등급은 유지된다.
- [ ] 앱 종료·재실행 후 사용 기록, 재화, 보유 카드, 선수단, 이름·사진이 복원된다.
- [ ] 사용량 반영 실패, 잘못된 이름·이미지, 저장 실패, 카드가 없는 상태를 안내하며 기존 데이터가 유지된다.

## 6. 후속 검토 범위

기획서에서 다음 기능은 후속 검토 대상으로 두었다. 첫 버전의 필수 구현 목록에는 넣지 않는다.

- 경기 시뮬레이션
- 선수 육성
- 카드 합성·거래
- 다른 사용자와의 대결

무작위 카드 팩, 지명타자, 투수진 구분, 타순, 구단 이름 변경은 후속 기능으로 확정된 것이 아니라 **도입 여부가 미정인 항목**이다.
